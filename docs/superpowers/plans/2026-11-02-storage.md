# Storage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the household's prose (briefings, Claude's answers) out of the log into markdown files in Synology Drive, give every plan a readable page beside its files, add one search across both, and bring edits made to a plan page in Drive back to Today as cards. The log stays the record.

**Architecture:** A new Drive v2 REST client (`drive.ts`) sits beside `synology.ts` and reuses its plumbing (`reach`, `verdict`, the `setDsmFetch` seam, the sid as the `id` cookie). `docs.ts` writes and reads documents under `/team-folders/<share>/<household>/`. It writes to Drive first and appends the event that names the file second. With no session, or when the write fails, it returns null and the caller keeps the inline body. Plan pages (`pages.ts`) are a deterministic render of replayed state. They are rewritten after the response to any plan change and recorded with `plan.doc`. A change in Drive is found by the `change_id` cursor and a hash comparison. It becomes a `plan.page.drift`, settled on the same `resolve_drift` card `drift.ts` already raises.

**Tech Stack:** Node 26 (`--experimental-strip-types`), `node:test`, no new dependencies. Synology Drive REST v2 (`/api/SynologyDrive/default/v2/`) and File Station (folders only). `api/tools/fake-dsm` grows a Drive. Single-file vanilla JS UI in `site/index.html`.

**Spec:** `docs/superpowers/specs/2026-11-01-storage-design.md`. It builds on `docs/superpowers/specs/2026-10-28-home-planner-design.md` (Constraints; Calls 8, 9, 13). Drive request and response shapes are in https://office-suite-api.synology.com/specs/Synology-Drive/openapi_v2.json. Read the spec first.

## Global Constraints

- Append-only JSONL log per household, replayed into state. Existing logs keep their inline bodies and must still replay. No rewrite or migration of old events.
- Effect first, then record. Write the file, then append the event that names it. If the write fails, fall back to the inline body and say nothing to the member.
- A plan page write is a best-effort follow-on, never an effect a plan change waits on. A plan edit must not fail because Drive is unreachable.
- Every Drive write is `PUT files/upload` (multipart) with `conflict_action: version`. `POST files` is never used for documents.
- `properties` and `app_properties` are read-only and not used. Drive labels are not used. A file's kind comes from its path and its frontmatter.
- The DSM `sid` stays in memory only, on the member's session. It never goes into a URL, a log line or a file. Drive gets it as the cookie `id=<sid>`.
- Dependency-light API: no YAML library. The frontmatter parser is hand-written for the fixed key set.
- Node 26 type stripping, no build step. No parameter properties and no enums (strip-only TypeScript).
- Every edit that moves money or changes a plan carries a reason. A change taken from Drive carries `why: 'edited in Drive'`, authored by the member who takes it.
- Integer cents everywhere. A page's `estimate` is cents.
- Restore scopes are unchanged (`thread`, `plans`). New ops go in existing scopes.
- The render of a plan page is deterministic: the same state gives the same bytes, with no timestamp.
- Everything found changed in Drive becomes a card, notes included, taken by the member who accepts it.
- Synology Drive 4.0.0 or later and DSM 7.2.2 nano3 or later. `PLANNER_ROOT` names the share, and the share is a Team Folder in Synology Drive.
- Out of scope: Drive webhooks (until their payload is observed), SQLite, KV stores, embeddings and any local index.

## Review Focus

1. **A briefing or answer whose Drive write fails, or that is written with no session, must never leave a pointer to nothing.** The event carries the inline body and no `doc`. Pinned in Tasks 7, 8 and 9 (refused upload → body in the log).
2. **A page that is behind the plan and was also edited in Drive must not offer to undo the app's own later changes.** The diff is three-way: it runs against the page as it was written (`pageAt`), not against the plan now. Pinned in Task 19.
3. **Search must never return another household's file**, even when Drive ignores `location`. Results are filtered to the household's folder prefix. Pinned in Task 16.
4. **When Drive is unreachable, a plan edit still succeeds, and the follow-on does not ask Drive again on every request.** The follow-on backs off for `PAGE_RETRY_MS`. Pinned in Task 15.
5. **A household restored on another NAS** must show a briefing's or answer's headline with *the full text is on the old NAS* (404, not 502), and must rebuild its plan pages. Pinned in Tasks 7, 11 and 20.

  Scalars render plain unless they would read back as something else. A value is double-quoted with `JSON.stringify` when it is empty, has leading or trailing space, contains `: `, ` #` or a newline, starts with one of `` "'[]{},#&*!|>%@` ``, or parses as an integer or `null`/`true`/`false`. Inside a list, `,` and `]` also force quotes. `null` renders as `null`, and lists render as `[a, b]`. The parser reads `null` and `~` as null, `-?\d+` as a number, `"…"` with `JSON.parse`, `'…'` with `''` → `'`, `[…]` split on commas outside quotes, and anything else as a trimmed string.

  ```ts
  /** Every live plan whose page the app has written: read it where its hash moved, and say what changed. */
  export async function checkPages(ctx: ToolContext, f?: DsmFetch): Promise<Event[]>;
  /** checkPages at most once per household per DRIFT_EVERY_MS. */
  export async function checkPagesNowAndThen(ctx: ToolContext, f?: DsmFetch): Promise<Event[]>;
  export const PAGES_FULL_EVERY_MS = 60 * 60 * 1000;
  ```
  `checkPages` steps:
  1. No sid, household or root → `[]`.
  2. `listChanges(householdFolder)`. If the cursor equals the one remembered for this store (in memory) and the last full look was under `PAGES_FULL_EVERY_MS` ago → `[]`. This is the safety net in case neither counter moves on the NAS.
  3. For each live plan with `page`, `getFile(byLink(page.doc.link))`, one at a time.
  4. Go on to the next plan when:
     - the file is gone → clear nothing and let `followOn` rebuild it, since a page holds no decision;
     - its hash equals `page.doc.hash`;
     - its hash equals the open drift's `theirs.hash`.
  5. Otherwise read it and `parsePlanPage` it.
     - Null → append `plan.page.drift { unreadable: true, changes: [] }`.
     - Otherwise diff against `pageAt(events, id, page.event)` and `pageView(now)`:
       - No changes → append `plan.doc { doc: toDocRef(file), event: page.event }`. This records their hash, as the calendar's etag-only update does.
       - Changes → append `plan.page.drift { theirs: toDocRef(file), changes }` and raise its card.
  6. A session lost, or a NAS that did not answer, stops the look, as in `lookForDrift`.

  A page whose `getFile` says no such file is treated as behind by `followOn`, through a new in-memory `gone` set keyed by plan, and is written by path, so its new link is recorded by `plan.doc`.
