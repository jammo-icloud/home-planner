# Bills on the envelope's page Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Execution:** subagent-driven development (chosen): a fresh implementer per task, a reviewer per task, a whole-branch review at the end. Tasks run in order, one at a time, in one worktree. An implementer sees only its own task, the sections above the first task, and the files the task names.

**Goal:** Part 1 of release 0.9.0: a bill may carry a Due, Auto Pay or Pay by date a member sets, its last receipt gives its day when it has none, a receipt is what says it is paid, `stillExpected` is redefined on that one function with no figure moving until a date is set, and the envelope's page gains a Bills section.

**Architecture:** Two ops (`bill.set`, `bill.remove`) are folded onto the budget as `bills`, keyed by envelope and a frozen `billKey`. One write tool, `set_bill`, is the only door. The page draws a section from the envelope page's own frame.

**Tech Stack:** Node 22.6+ running TypeScript by type stripping, `node:test`, an append-only JSONL log, one vanilla-JS page (`site/index.html`) with `site/tokens.css`. No new source file; new tests only.

**Spec:** `docs/superpowers/specs/2026-11-09-calendar-day-page-design.md`: Intent, Goals, Non-goals, Anti-goals, "Two parts", "Part 1: Bills", and the Part 1 lines of "The server", "Copy rules" and "Accessibility and the phone" (binding; where this plan and the spec disagree the spec wins, except the Rulings below). **Inputs:** `docs/superpowers/specs/2026-11-07-envelope-pages-design.md`, `docs/superpowers/design/2026-11-10-redesign-gap-outline.md`, `docs/superpowers/design/2026-11-10-carry-over-ledger.md`.

**Scope:** Part 1 stands alone. It adds no Calendar change, deletes nothing, and does not bump the version (the day page plan does that once for 0.9.0). ## Review Focus

A reviewer rejects a task for any of these, whatever else is right.

**What would silently change a figure.** Each is a trap in today's `pace`, with a test in the named task and a shape in Task 1's fixture.

1. **Merging by bill before counting by charge.** `pace` counts two fixed charges of one payee in one envelope separately: one landing leaves the other expected. An undated bill's expected money must stay charge by charge, or `$60` vanishes. Task 3 (`charges`), Task 4 (`billsExpected`), Task 1's hand-worked `home` figure.
2. **A refund is a landing.** `pace` builds `landed` from `e.lines`, and a line can be money in. Dropping refunds to make "a receipt" tidy adds `$146` to such a month. Task 3 (`charges[].landed` keeps them, `receipts` does not), Task 1's hand-worked `util` figure.
3. **Two walks.** `pace` reads `t.category` to place a charge and `line.category` to see it land. Unifying them moves figures on split receipts. Task 3, Task 1's `subs` row in September.
4. **`clock.complete` zeroes the figure on the last day and for past months.** It stays in `pace`, outside the function. Task 5, Task 1's last-day rows.
5. **The envelope `pace` leaves out.** `pace` still skips an envelope with nothing funded and nothing spent; `billsOf` does not. Task 5, Task 1's `spare` envelope.
6. **A line missed in `freeze` or `thaw`:** every date vanishes on the next append, with no error. Task 2's `apply` test and Task 1's whole-replay against step-by-step test.
7. **A dated bill paid across the month's edge.** Due on the 1st, paid on 31 October: November's date is paid. Counting a dated bill by calendar month says "no receipt" for ever. Task 4.
8. **A match that reaches too far.** A key contained in a longer payee absorbs that charge, and a date then moves the figure: only inside one envelope, and only the longest key that fits. Task 3.

**The inputs most likely to bite a person**, each with its test in the owning task.

1. **A day past a short month's end:** the 31st reads February's last day; a quarterly date on 31 January lands on 30 April and 31 July. Task 4.
2. **A payee that is all digits:** `billKey` is empty, so a name typed "1234" is refused with words and such a receipt is nobody's bill. Tasks 3, 6.
3. **Two people with the page open:** one removes a hand-named bill, the other saves a date on it: told in the form's slot, what was typed kept. Task 6 (the refusal), Task 7 (the slot).
4. **The same receipts under two live budgets:** listed in each, with its own date in each. Task 3.
5. **A bill re-sorted away, then back:** its date follows, and comes home with the receipts. Task 3.

## Rulings

The spec leaves these open; each is settled here and carried by the named task.

1. **`bill.remove` carries `name`.** The spec's op is `{ budget, envelope, bill }`, but its `describe()` must say "removed the bill Example Water from Utilities" and the fold deletes the record, so nothing else can supply the name. Task 2.
2. **A name finds a bill in either direction.** "A `name` takes the envelope's bill whose key it contains" cannot be read one way only: "power" has to find `example power` for "say more of it" to mean anything. An exact key wins; otherwise a bill matches when `billKey(name)` contains its key or its key contains `billKey(name)`. Task 6.
3. **A receipt part goes to one bill.** Among the bills listed in the envelope that hold a record: the exact key, else the longest key the receipt's key contains, ties by key order. Task 3.
4. **`about` is the sum of the bill's fixed charges' `typical`.** Fixed charges of one envelope sharing a key are one bill, and today's `stillExpected` sums them. Task 3.
5. **An undated bill with several charges is paid in a month only when every charge has landed.** Otherwise `stillExpected` and "paid" could disagree, which the spec forbids. Its still-expected money is the unlanded charges' `typical`. Task 4.
6. **Refunds.** A money-in part counts as a landing for an undated charge (as `pace` counts it now), and is never a receipt: it does not pay a date, is not `lastPaid`, and is not listed. A month with only a refund has no occurrence: nothing is expected and nothing was paid. Task 3, Task 4.
7. **A dated bill is one payment:** a date paid by any receipt for the bill expects nothing, whatever its charges. Task 4.
8. **A bill does not follow into a savings envelope.** With several to follow to it goes to the one holding the latest receipt, ties by `order`. Task 3.
9. **`billsOf` includes savings envelopes** because `pace` counts their fixed charges today; `get_month` sends `bills: []` on one, and `set_bill` refuses one. Task 3, Task 6.
10. **`since` moves only when the date does.** Saving the same date again keeps it; a cleared bill has `since: null`. Task 2.
11. **`byHand` is never lost:** a later `bill.set` without it keeps a hand-named bill hand-named. Task 2.
12. **The sub-line is the server's words,** `line` from `billLine`, so they are tested. About and last paid both show when both are known, in that order. Task 6.
13. **The date's words live in `billDateWords`,** lower-case for sentences, the first letter raised on the page's line; "Auto Pay" keeps its capitals everywhere. Task 2.
14. **`Next date` starts empty on a bill with no such date,** and at its `on` on Change. Task 7.
15. **A closed month:** rows with no action and no "Add a bill". Task 7.
16. **The "Add a bill" row is the shipped `.add-row`:** `envLine`'s word and button would say it twice. Task 7.
17. **One form at a time across the page.** Opening a Bills form cancels any other, and Each month's Change and the goal form cancel an open Bills form. The question form has no Cancel and stays. Task 7.
18. **`openBudgetAt` is not changed here:** its focus key is Part 2's. This part supplies the target, `data-key="bills"`. S19 is pinned as kept. Task 7.
19. **The refusals the spec does not word** are in Task 6's tests, with `no bill ${x} in ${label}` as the 404. The form's own: "Give it a name" (0.7.0's words) and "Choose the next date." Tasks 6, 7.
20. **The form's heading is an `h3.ep-q`,** and is what scrolls to the top on a phone. The action's accessible name carries the bill: "Set a date for Example Power", "Change the date on Example Power". Task 7.
21. **The Kind group's label is a `<label>` the `.seg` names by `aria-labelledby`,** so `.ep-f label` styles it. Task 7.
22. **A card's summary and effects** beyond the spec's are in Task 6's tests, each ending "No money moves". Task 6.

## Interfaces: what the Calendar day page reads for its money rows

Part 2 builds `MoneyRow` and `money[]` from exactly these exports of `api/src/analytics.ts`, and reads nothing else of this part except the section heading. They are defined in Tasks 3 and 4.

```ts
export interface BillPaid   { readonly txnId: string; readonly day: Day; readonly amount: Cents; readonly payee: string }   // money out, positive
export interface BillCharge { readonly key: string; readonly typical: Cents; readonly lastDate: Day; readonly landed: ReadonlySet<Month> }
export interface Bill {
  readonly envelope: EnvelopeId;   // where it is listed and drawn now (it follows its receipts)
  readonly key: string;  readonly name: string;  readonly byHand: boolean;
  readonly date: BillDate | null;  // { kind: 'due'|'autopay'|'payby', per, day | on }
  readonly since: Day | null;      // the household day the date was given
  readonly about: Cents | null;    // the typical amount; null when the receipts give none
  readonly charges: readonly BillCharge[];  readonly receipts: readonly BillPaid[];  readonly lastPaid: BillPaid | null;
}
export interface BillOccurrence {
  readonly month: Month;
  readonly day: Day;               // the date as it falls; undated, the last receipt's day held to this month's last day
  readonly dated: boolean;
  readonly paid: BillPaid | null;
  readonly about: Cents | null;    // what this occurrence still expects; null when paid or the receipts give none
}
export function billsOf(state: State, budget: BudgetId, opts?: { fixed?: readonly FixedCharge[] }): ReadonlyMap<EnvelopeId, readonly Bill[]>;
export function billOccurrences(bill: Bill, from: Day, to: Day): readonly BillOccurrence[];  // those whose day, or whose receipt's day, is in the window
export function billsExpected(bills: readonly Bill[], month: Month): Cents;                  // the short row's sum
```

The mapping onto the spec's `MoneyRow`:

- Skip an envelope whose `state.budgets.get(budget)!.envelopes.get(id)!.sinking` is set.
- `paid` set: kind `'paid'`, `day: paid.day`, `amount: fmtExact(paid.amount)`. Keep it only when `paid.day` is in the window.
- `paid` null and `dated`: kind `bill.date.kind`, `day`, `about: fmt(about)` when not null, `noReceipt: day < today`. Draw it when `day >= bill.since` or `monthOf(day) === monthOf(today)`, and `day` is in the window.
- `paid` null and undated: kind `'bill'`, only when `about !== null` and `month >= monthOf(today)`, on `day`.
- The short row: `view.available < billsExpected(bills, monthOf(today))` for an envelope with a figure, on today, while the budget's current month is open.
- A money row opens the envelope at `openBudgetAt(budget, envelope, 'bills')`, which focuses the heading with `data-key="bills"` once Part 2 has grown the third argument.
