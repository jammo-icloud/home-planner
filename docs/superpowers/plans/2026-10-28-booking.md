# Booking Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Friends with no NAS account ask to stay through a passwordless, allowlisted page; the household decides on Today; approval puts the nights on the Household calendar and emails the guest.

**Architecture:** A second, minimal session type (`GuestSessions`) on a cookie scoped to `/book`; an allowlist and every booking as events in the household log under a `bookings` scope; one `approve_booking` write tool whose `effect` (from the Calendar plan's effect stage) creates the calendar event and sends the email before the decision is recorded; SMTP spoken directly from `api/src/mail.ts` with no dependency. The guest page is a separate static file with none of the member chrome.

**Tech Stack:** As the project. Requires all three Home Planner plans complete.

**Spec:** `docs/superpowers/specs/2026-10-28-booking-design.md`. Read it first; every constraint there is a global constraint here.

## Global Constraints

- `BOOK_URL`, `BOOK_HOUSEHOLD`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM` — booking is off until **all** are set; members see why at `GET /api/settings`; guests see a plain "not available" page.
- `POST /book/start` always answers `{ ok: true, message: "If that address is one we know, a link is on its way." }` — identical whether or not the email is on the list, over the limit, or booking is off.
- Code: six digits, expires 10 minutes. Magic link: single-use token, expires 24 hours. Guest session: 30 days. Rate limit: 5 code requests per email per hour, 20 per IP per hour; over the limit, the same answer and nothing sent.
- The magic link is built from `BOOK_URL` only.
- Guest cookie: name `book-guest`, `Path=/book`, `HttpOnly`, `SameSite=Lax`, `Secure` unless `COOKIE_INSECURE=1`.
- A guest session can reach only routes under `/book`; `sessionOf` never accepts a guest cookie.
- Nights are exclusive. Taken = approved stays ∪ other guests' pending requests ∪ member blocks. A guest never sees why a night is taken or who else is coming.
- The guest actor is `guest:<email>`; it may author only `proposal.offer` with `prompt.kind: 'booking'`, `booking.cancel`, and `booking.change` (replay enforces).
- Approve: calendar event → email → `proposal.decide` + `booking.confirm` in one write; on email failure the event is deleted and nothing is appended. Decline: email → `proposal.decide`.
- Suggest other dates: declines the original, appends `booking.suggest`, emails; suggested nights are not held; the guest's acceptance is a fresh offer marked "you suggested these."
- Four plain-text emails: code and link; confirmed; declined with reason; other dates suggested. From `SMTP_FROM` with the household label as display name.

## Review Focus

1. **The same email requests two overlapping stays.** The second request must be refused as overlapping their own pending/approved stay, not shown as "taken by someone." Pinned in task 5.
2. **A guest reopens an old magic link after signing in on another device.** Single-use means the token is dead; the page says to request a new one. Pinned in task 3.
3. **Approval when the nights were taken in between** (two guests, one decided first) — `approve_booking.run` re-checks availability at decision time and refuses with the overlap named. Pinned in task 6.
4. **SMTP accepts the connection and rejects the recipient** (550) — treated as a send failure, event deleted, card stays waiting with the SMTP reply in the error. Pinned in task 2.
5. **`BOOK_HOUSEHOLD` names a household that does not exist** — booking is off and the boot log says so. Pinned in task 1.

**Interfaces:**
- ```ts
  export interface BookingConfig { url: string; household: string; smtp: { host: string; port: number; user: string; pass: string; from: string } }
  export function bookingConfig(env: NodeJS.ProcessEnv): BookingConfig | { off: string /* which variable is missing */ };
  // ops, scope 'bookings':
  | { op: 'guest.allow'; email: string; name: string; why: string; contact?: ContactLink }
  | { op: 'guest.revoke'; email: string; why: string }
  | { op: 'booking.block'; from: Day; to: Day; why: string }          // nights from (inclusive) to (exclusive)
  | { op: 'booking.unblock'; block: EventId; why: string }
  | { op: 'booking.confirm'; request: EventId; email: string; arrive: Day; depart: Day; headcount: number; cal_id: string; original_cal_id: string; evt_id: number; ical_uid: string; dav_etag: string }

  | { op: 'booking.change'; stay: EventId; arrive: Day; depart: Day; headcount: number; note: string }   // by the guest; raises a fresh offer
  | { op: 'booking.suggest'; request: EventId; email: string; arrive: Day; depart: Day; why: string }
  // State gains: readonly guests: ReadonlyMap<string /* email, lowercased */, { name; allowedBy; at; contact? }>; readonly stays: ReadonlyMap<EventId, Stay>; readonly stayBlocks: ReadonlyMap<EventId, { from; to; why }>
  ```
  `REQUIRES_WHY` gains `guest.allow`, `guest.revoke`, `booking.block`, `booking.unblock`, `booking.cancel`, `booking.suggest`. Emails are lowercased and trimmed in the fold.

### Task 6: Approve, decline, suggest

**Files:**
- Modify: `api/src/tools.ts` (`approve_booking.effect`), `api/src/booking.ts` (`decline`, `suggest`, `acceptSuggestion`, the four email texts), `api/src/server.ts` (`POST /api/bookings/suggest`; `POST /book/accept-suggestion`), `api/src/offers.ts` (`decide` passes `why` to a tool's `onDecline?` hook — used here to email the reason)
- Test: `api/test/booking.test.ts` (with the fake SMTP and fake DSM)

**Interfaces:**
- `approve_booking.effect`: `ensureHouseholdCalendar`; `createEvent` all-day `arrive → depart` summary `"<name> staying (<n>)"`; `sendMail(confirmed)`; on `MailError` → `deleteEvent` then rethrow as `ToolError(msg, 502)`; returns `[booking.confirm …]`.
- `Tool.onDecline?(args, ctx, why?): Promise<void>` — runs **before** the decline is appended; `approve_booking.onDecline` sends the declined email with `why`.
- `suggest(ctx, offerId, { arrive, depart, why })`: `decide(declined, why)` (which emails), append `booking.suggest`, `sendMail(suggested)` with the link.
- `acceptSuggestion(ctx: guest, suggestId)`: a new `request()` for the suggested dates whose offer `summary` is prefixed `"You suggested these: "`.
- **Cancel and change, by the guest.** `cancelStay(ctx: guest, stayId, why)`: on a pending request, appends `booking.cancel` and the fold marks that offer `replaced` (withdrawn — a guest never *decides* a proposal); on an approved stay, appends `booking.cancel` and raises a member card `release_stay { stay }` (prompt `booking`) whose `effect` deletes the calendar event and returns `[booking.release { stay }]` — members "simply acknowledge" by approving it; the nights are free from the moment of `booking.cancel`, not the acknowledgement. `changeStay(ctx: guest, stayId, { arrive, depart, headcount, note })` is `cancelStay` followed by `request()` for the new dates, in one call, with the new offer's summary prefixed `"Changed from <old dates>: "`. New op `booking.release { stay: EventId }` (scope `bookings`).

- [ ] **Step 1: Write the failing tests** — approve: one DSM create, one mail, then decide + confirm with the same `at`; SMTP `550`: one DSM create, one DSM delete, no append, offer still open, error names the reply; decline: one mail with the reason, then decide; suggest: original declined, one `booking.suggest`, two mails; accept-suggestion: a fresh open offer whose summary starts `"You suggested these"`; approving a request whose nights were taken in between is refused with `/taken/` and no mail is sent; cancel of a pending request → its offer is `replaced` and the nights are open; cancel of an approved stay → a `release_stay` card waits, the nights are already open, and approving it makes one DSM delete; change → old cancelled, new offer open with the `Changed from` prefix.
