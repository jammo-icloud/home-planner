# Rulings made while building Home Planner

Every decision the orchestrator took where the spec, the plan and a reviewer did not settle it, in the order it was made, each with what it costs if it was the wrong call. Source: the four SDD ledgers, 28–30 October 2026. Rulings on Fable, work by Opus and Sonnet subagents, every task reviewed by a fresh reviewer, every branch reviewed whole before merging.

## Synology sources (sessions, calendar, contacts, files, settings)

- Ruling: T9 tests may use either `setDsmFetch` with an in-process fake fetch or an in-process fake-dsm on port 0 with `DSM_URL` set before import; the implementer picks the simpler and says which — the plan leaves it open and both satisfy the test's assertions — cost if wrong: a slower test file, nothing else.
- Ruling: the per-member appearance event is named `scheme.set` (the design document's name), lives in Plan 1 Task 8/9 with the other settings ops, scope `settings` — the design left the scope to engineering and this keeps per-member settings together — cost if wrong: a rename across two files.
- Ruling: the app no longer sends SYNO.API.Auth logout, so the NAS-side session lingers after a member signs out of the app — the sign-out route will call DSM logout with the session's sid (best effort, errors ignored) once dsm() exists; carried into Task 3's dispatch — cost if wrong: one extra DSM call on sign-out.
- Ruling: `fakeDsm` is exported from synology.test.ts, which registers tests; a file that imports it re-runs them. Task 8's settings.test.ts (the first other file to need it) moves `fakeDsm` to `api/test/fake-dsm-fetch.ts` and synology.test.ts imports it from there — cost if wrong: a small test-only move.
- Ruling: the sign-out DSM logout stays awaited for now; Task 9 (which brings setDsmFetch and the test) reorders it — revoke, clear the cookie, respond, then fire the DSM logout unawaited with a swallowed rejection — cost if wrong: a sign-out that waits on a hung NAS until then.
- Ruling: the placeholder /api/calendars gate sits after activeStore(); Task 9's real calendar routes check requireSid before any household lookup, since calendars need no household — cost if wrong: a restored session sees "no household is open" instead of "sign in again".
- Ruling (plan-mandated finding): the plan's "any set failure not 9007/9009/9017 is EtagMismatch" stands, but when the follow-up getEvent returns the same dav_etag the event did not change, so the original SynologyError is rethrown instead — Task 10 narrows the code list against the real NAS — cost if wrong: a real mismatch misreported as a NAS error only if DSM rejects a stale etag without having changed the etag, which is contradictory.
- Ruling: a comma in a name can be uploaded but downloadFile/listFolder refuse it; Plan 2 Task 6's attachmentPath also refuses a comma, so no attachment can be written that cannot be read back — carried into that task's dispatch — cost if wrong: one more character a file name cannot have.
- Ruling: restoring the settings scope into a household whose Household calendar is already set is refused at apply time with no preview warning; Plan 2 Task 8 (restore collisions) adds a 'settings' collision kind for calendar.household — carried into that dispatch — cost if wrong: a restore that fails late instead of early.
- Ruling: scheme.set and calendar.conflicts are personal preferences and are excluded from Activity — cost if wrong: a change nobody needed to see.
- Ruling: the household's target calendar must be writable by every member, since Plan 3 writes plan events with the acting member's sid; POST /api/calendars/target accepts the Household calendar or a calendar the chooser owns and has shared RW to every other member (sharingOf succeeds for the owner), otherwise 400 "share it with <name> first" — carried into the final fix wave of this branch — cost if wrong: a member's due date fails with a 502 naming DSM's refusal, which the card shows.
- Ruling (Important 7): a Household calendar can be replaced: `calendar.household` may follow an earlier one only when it carries `replaces: <the current cal_id>`; the fold swaps household (and `by`) and clears `target` if it pointed at the old one; `POST /api/calendars/household { replace: true }` creates a new one that way — cost if wrong: an extra field on one op.
- Ruling (Minor 4): renaming the Household calendar (spec "editable") is carried to Plan 3 Task 9's Settings UI with a `Cal.Cal set` client call — cost if wrong: a rename done in Synology Calendar instead.

## Plan (the board, cards, asks, research)

- Ruling: T2 adds the optional `plan?: PlanId` field to `thread.ask`, `thread.note` and `thread.answer` in types.ts (a type-only addition) so `board()`/`card()` can read it; T3 wires it through `askInThread` and the tools — cost if wrong: none; T3 would add the same field.
- Ruling: a `ReplayError` raised by a plan route's direct append becomes `ToolError(message, 400)` inside the `plans.ts` helpers (one shared wrapper), not in the global handler, which keeps 500 for unexpected failures — cost if wrong: a 400 that should have been 409; the message is the same.
- Ruling: an open ask lapses when its plan is removed or when the asked member leaves the household (fold clears `asked`, retires the answer_ask offer, owner unchanged) — carried as a pre-review addition — cost if wrong: an ask that should have survived a plan's removal, which cannot be answered anyway.
- Ruling: the implementer's uncovered decisions stand — detach/unlink/unblock of a missing key is refused; asking the owner or a non-member is refused; a block must end after it starts; a shelf is a plan with live children; Draft.plans holds replaced Plan objects — cost if wrong: small fold changes in a later task.
- review clean (Opus). Rulings on its judgment calls, carried into Task 3's dispatch as fold additions:
- Ruling: a shelf's own state is never read for placement; board() derives nothing from it and shelves are strips, not column cards — cost if wrong: none visible.
- Ruling: a child's area is its parent's: plan.create with a parent refuses an area different from the parent's (`'an item lives in its shelf's area'`), and plan.set with area on a shelf moves its live children with it — cost if wrong: a shelf split across rows, which the design never shows.
- Ruling: when a member is removed, their live plans pass to the member who removed them (the event's author), owner changed in the fold, so no plan is stranded with an owner who cannot be asked — cost if wrong: a plan that should have been archived instead is now owned by the remover, who can remove it.
- Ruling: `areas.set` refuses to drop an area that live plans still use (`'"Trips" still has plans in it'`), matching the Settings spec's "Remove only when empty" — carried into Task 3's fold additions — cost if wrong: an area rename needs two steps (add new, move plans, drop old).
- Ruling: with showDone, done cards appear in the Doing lane with state 'done' (the UI renders them quietly); money reads only the month of today and is null when that month is not open, never a stale figure — cost if wrong: a cosmetic lane choice.
- Ruling: daysInState must count days in the household's TZ, the same way the server computes `today`; Task 4 passes the TZ (or a dayOf(at) helper) into board()/card() and adds a test for a stateAt just before local midnight — cost if wrong: a Doing clock off by one day near midnight.
- Ruling: research from a card never offers a money-moving tool to Claude (filtered from the tool list by touches) — cost if wrong: a money card Claude could have raised from research must come from the Today thread instead, which is the spec's intent.
- Ruling: plan.set may not change an item's area while it has a parent (same message as create) — cost if wrong: none; re-parenting does not exist yet.
- Ruling: plans that pass to the remover on member removal have their open ask cleared and card retired — cost if wrong: an ask the new owner must re-send.
- Ruling: one plan per research answer (offer() re-runs create_plan with a fresh id) and history showing a "suggested" line per research card both stand — cost if wrong: a noisier history.
- Ruling: a research card whose approval the fold restricts to one member (ask_to_take to the owner; answer_ask to the asked) is shown to both and the other member's click gets the fold's 409 message, as the plan says — Task 5 may hide the buttons where the viewer cannot act — cost if wrong: one explained refusal.
- Ruling: `/api/plans/:id/ask` asks Claude; `/api/plans/:id/ask-to-take` asks a member (the plan listed one path for both) — cost if wrong: one route name in Task 5.
- Ruling: board()/card() default tz to the process TZ (the household's, per DEPLOY.md) so Claude's tools and the routes share one Doing clock — cost if wrong: none while one household per deployment TZ holds, which DEPLOY.md already assumes.
- Ruling: `.hp` wraps <main> only for now (the phone tab row sits between header and main); Plan 3 Task 9 re-wraps header + main with the tab bar outside — cost if wrong: the container query measures main, which is the same width.
- Ruling (Important 8): a decline "returns it as a card to the asker" is met by the quiet line with the reason in Today plus the plan back on the owner's board without the asked chip; the design language says a decision is never a card — the spec wording is amended in the docs commit — cost if wrong: the owner reads one line instead of a card.
- Ruling (Important 10): the restore preview reports a plan owned by, or asked of, an account that is not a member of the target as a collision (kind 'owner'); restore stays refused until that account is a member or the owner restores elsewhere — cost if wrong: a restore that needs a member added first.
- Ruling (ask cards, Critical 1): the `answer_ask` offer is raised wherever `plan.ask` lands (one place, in the fold's append path or a shared writer used by both the route helper and the tool's approval), rendered on plain paper with Take it / Decline for the asked member only and "waiting on <name>" for others, never listed as waiting on anyone else, and retired to a one-line "Taken by …" / "Declined by … — 'why'" — cost if wrong: one more place that knows about ask cards.
- Ruling (Important 6): `daysInState` is null outside doing in BoardCard and CardView, and the tool description says so — cost if wrong: a briefing that cannot mention how long a thinking item has waited, which is the point.
- Ruling: the ask card stays two appends (ask then card); a failed second append leaves a plan asked with no card — deferred, as the final review allowed — cost if wrong: an ask the owner must withdraw and re-send after a crash between two writes.
- Ruling: the fix-wave commits carry the trailer of the model that wrote them (Opus 5.5); history is not rewritten — cost: none.
- Ruling: one final targeted commit (omit the overwrite part unless true; fake DSM models the real semantics; tests) instead of carrying a silent-drop into main — the skill's one-wave rule guards against loops, and this is a two-line, test-pinned change; I verify it with the suite myself and merge without a further review round — cost if wrong: a bug in a path only the fake exercised, caught by Task 10's check on the real NAS.

## Calendar and Today (the shell, drift, appointments, rails, week)

- Ruling: `checkDrift` runs on `GET /api/thread` at most once per household per 10 minutes (an in-memory stamp keyed by store.path), and always on `POST /api/calendar/check`; the plan's "on every thread load" is kept in spirit without a DSM call per link per refresh — cost if wrong: a drift noticed up to ten minutes late.
- Ruling (owner-directed, 2026-10-29): Task 9 (the shell, Settings, More, Appearance) runs FIRST in this plan, before Tasks 1–8. The Calendar tab is present from the start and shows the design's quiet "unavailable" panel ("The calendar arrives with the next release" in the app's voice) until Task 8 lands its week view; everything else in Task 9 is built in full. Order after that: 1, 2, 3, 4, 5, 6, 7, 8, 10 — cost if wrong: one placeholder panel for a few tasks.
- Ruling: `Proposal.args` is required for a tool with an effect; Task 3 makes the run call sites (server.ts tools route, claude.ts) record args on every proposal so no tool can forget — cost if wrong: a 500 "proposal has no args" on the first effect tool that forgets.
- Ruling: when an effect succeeds and the append is then refused, `decide`/`commit` call an optional `tool.compensate?(args, ctx, extra)` before rethrowing; Task 3 adds it and `syncDue`/`syncBlock` implement it by deleting the event they made — cost if wrong: an orphan event on the calendar after a rare write race.
- Ruling: Task 3 adds an in-flight guard keyed by offer id in decide() (a second approver fails before the effect runs) and the compensate hook on a refused append in both decide and commit — cost if wrong: an orphan calendar event after two members approve the same card within one NAS round-trip.
- Ruling: renaming an area that has plans needs its own op — `areas.rename { from, to }` moves the plans and the list entry in one fold; carried into Task 2 (the next fold task) with the Settings Rename control enabled for every area — cost if wrong: an op the UI could have expressed as set.
- Ruling: drift detection covers plan-linked events only; standalone appointments (State.appointments without a plan) are not drift-checked in this release and their etag is not refreshed — cost if wrong: an appointment Claude scheduled with no plan can be moved on a phone without a card saying so.
- Ruling: a bypass session may set a new due date or block (no event, response says sign in again) but any change that would leave an event the plan no longer has (clearing/changing a synced due, letting a linked block go, removing a plan with events) is 409 "sign in again" — cost if wrong: a member without a NAS session waits to sign in before clearing a date.
- Ruling: `Tool.effect` receives the proposal's stored events and `Tool.effectFirst` orders an effect's events before the stored ones; both stay — cost if wrong: two small additions to the tool interface.
- Ruling: a due or block card cannot be approved on a session without a NAS sid (NeedsDsm); the card path refuses where the route path may wait — cost if wrong: a sandbox approval that must be done after signing in.
- Ruling: "Leave both" records the calendar's current etag (or unlinks a deleted event) with the resolve so the same drift is not asked again; an etag change that keeps the plan's times is recorded quietly with no card; "Put the calendar back" restores the plan as it is now — all three stand — cost if wrong: a card re-asked, or a calendar restored to a later plan state.
- Ruling: `on:'mine'` records the asker in the args and the effect refuses approval by another member (409 "only <asker> can put this on their own calendar") since the app never writes a partner's calendar — cost if wrong: a card the other member must leave to its asker.
- Ruling: the clash check for `on:'household'` includes the plans' target calendar when it differs from the Household calendar — cost if wrong: one more calendar read.
- Ruling: an existing `plan` on propose_event links the appointment to that plan (kind 'appointment') so drift covers it — cost if wrong: a second appointment on the same plan replaces the first link.
- Ruling: no "Reminder 1 hr before" line until DSM's reminder format is confirmed; a start earlier than now on today's date is refused — both stand.
- Ruling: renaming or moving a plan in the app syncs the title and description to its linked events with the stored etag (a drift if the etag moved), so an in-app rename is never later read as a phone rename — carried into Task 5's additions — cost if wrong: one more NAS set per rename.
- Ruling: where my brief's breakpoint (760) and components.css (1040 for the Yours side column) disagree, the reference CSS wins — moved to the final wave with the other layout polish — cost if wrong: a side column that appears 280px later.
- Ruling: "New event" opens the composer with "Schedule "; "Block nights" disabled until booking — both stand.
- Ruling: in askInThread's research path, every RESEARCH_WRITES tool with a `plan` input has `args.plan` overwritten with the researched plan before run (absent → filled; differing → replaced) — cost if wrong: research can never act on a second plan from one card, which is the design's intent.
- Ruling (Important 6): every NAS event call resolves the link's calendar through the acting member's own listing (one resolver, used by where(), place, takeOff, lookForDrift, settleDrift); a 9009 is read as "deleted" only when the acting member lists the link's calendar, otherwise the look skips that link and logs — cost if wrong: one listCalendars per sync.
- Ruling (Important 2): an on:'mine' proposal card is shown only to its asker; on any card others can see, an event from a non-Household calendar is named by calendar and time only, never its title — cost if wrong: a less specific clash line for the partner.
- Ruling (Important 1): a briefing written without the calendar is replaced the first time someone with a NAS session looks that day; the line reads "The Household calendar was not read for this briefing." — cost if wrong: one more Claude call on such days.
- Ruling (Important 4): an unlinked due date or block is drawn and said as "not on the calendar"; the next look with a NAS session places it — cost if wrong: an event created a little after the date was set.
- Ruling (Minor 2): runEffect keeps a SynologyError's own status (SessionLost stays 409) — plan said 502; the spec's "sign in again" handling needs the 409.
- Ruling (Minor 11): calendar.ts is split mechanically into calendar.ts (sync/place), drift.ts, appointments.ts, calendar-view.ts with calendar.ts re-exporting names tests import — cost if wrong: an hour of a reviewer's time.
- Ruling: one closing commit (Sonnet) for New Important 1 + saysUnread + DEPLOY sharee row + ownedBy→original_cal_id; the rest are leftovers for the final list — the Important costs NAS calls and log noise until the calendar's maker opens the app, and the fix is local — cost if wrong: one more small diff to read before merge.

## Booking (the guest door, requests, approval, mail)

- Ruling: booking is built on the Calendar branch head before that branch's final wave; main takes calendar-and-today (with its wave) first, then booking is merged on top with any conflicts resolved by the orchestrator — cost if wrong: one merge to resolve by hand.
- Ruling: AUTH PLAIN is refused over a non-TLS connection unless `SMTP_PLAIN_AUTH=1` (for a relay on the NAS itself); carried as a pre-review addition and into Task 1/3's config wiring — cost if wrong: an owner with a LAN relay sets one more variable.
- Ruling: a guest's proposal.offer carries no events (the fold refuses a guest card with events) — carried into Task 5 — cost if wrong: none; approve_booking's events are supplied by its effect.
- Ruling: the BOOK_HOUSEHOLD existence check also runs lazily when /book is first hit after boot (cached once it passes), so creating the household later needs no restart — carried into Task 3.
- Ruling: two confirmed stays may not share a night (fold refuses "taken"); blocks do not count in the fold (the route checks them) — stands.
- Ruling: the implementer's hardening stands — five wrong codes lock that address's codes; a successful sign-in spends every outstanding link and code for the address; a revoked guest is refused or signed out.
- Ruling: Referrer-Policy strict-origin on the confirm page (no-referrer would null the Origin on the POST and refuse every guest); confirmed.
- Ruling: a `snoozed` request keeps its nights — it is undecided, and freeing them would let two guests hold one night — costs a snoozed-forever request blocking nights until someone decides it (the card is still on Today).
- dispatched on 71d3e57 (Opus). Rulings carried: /book/change = cancelStay+request with old stay nights treated free via args.replacesStay; effect re-checks nights; onDecline mail failure keeps the card open (502); suggest link from BOOK_URL only; a suggestion accepted once.
- Ruling: changeStay as cancel+request without replacesStay is accepted — the new nights are checked with the old stay exempt before anything is appended, so the only gap is a true race between two appends — cost if wrong: a guest whose old stay is cancelled and new request not raised, visible in /book/mine, re-requestable.
- Ruling: booking.change stays in the fold unused rather than reopening the validator set — listed as a leftover.
- Ruling: release_stay is authored by the guest who cancelled, the fold admitting a guest `release_stay` only when prompt.ref is that guest's own booking.cancel of args.stay — Activity then names who cancelled — cost if wrong: one more clause in the guest rule.
- Ruling: a cancelled stay with an event and no release card gets its card raised on the next thread load (reconcile like raiseAskCards) rather than making the two appends atomic — cost if wrong: a card that appears a page-load late.
- Ruling: GET /book while booking is off stays the quiet 200 page Task 2 tested ("isn't available right now"), not a 404 — a guest is told nothing either way and a page in the app's voice beats a bare 404 — cost if wrong: one status code and one test.
- Ruling: book.html loads Satoshi from fontshare as index.html and the Guest mockups do — the design is binding and members already make that request; the public page's third-party fetch goes on the final list for the owner — cost if wrong: one <link> line.
- Ruling (I5): a change to a confirmed stay holds the old stay until the change is decided — the new card carries replacesStay, the old nights stay taken for others, approval's effect creates the new event, mails, deletes the old, and booking.confirm{replaces} frees the old stay in one append; decline leaves it — the spec says the stay stands until decided; the plan's cancel-then-request lost it — cost if wrong: a change the household wanted to free nights at once now waits on a decision.
- Ruling (I6): an Arrival note in Settings → Guests (op guests.arrival, scope settings) rides in the confirmation mail; the page promises it only when one exists — cost if wrong: one settings op.
- Ruling (operational): /api/auth/login gets a per-IP limit (10/min, 100/h) since DSM's reverse proxy exposes the whole origin at planner.example.com; DEPLOY says what whole-origin exposure means and how a path-capable proxy narrows it — cost if wrong: a member locked out for a minute after ten wrong passwords.
- Ruling (M16): with booking off, an existing booking card may still be declined, never approved — cost if wrong: a decline whose mail cannot go (502 says so).
- Ruling (M7): suggest keeps two mails (decline, then the suggestion with its link) — a single mail would need the suggestion's id before the append — listed for the owner.
- Ruling (cap): at most 3 open requests and 60 pending nights per guest — cost if wrong: a friend planning four separate visits asks twice.
- Ruling: one closing commit (resume the wave implementer) for the login race (take the slot before DSM, refund on non-401; 20 concurrent wrong logins → at most 10 reach the fake DSM) + the Approve button reload + the log prefix + the DEPLOY Auto Block line; the rest are leftovers — the race defeats the only throttle on the internet-exposed password check — cost if wrong: one more small diff to read.
